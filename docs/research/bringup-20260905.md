# First bring-up — ESP32-S3-Touch-AMOLED-1.8

**Date:** 2026-09-05
**Unit:** Waveshare ESP32-S3-Touch-AMOLED-1.8, SKU 29957, Wi-Fi STA MAC `90:70:69:fe:84:30`
**Toolchain:** ESP-IDF v5.5.3, macOS, board on `/dev/cu.usbmodem3101`

## Goal

Stand up the workspace, prove the toolchain builds and flashes for this board, and
establish the board's real hardware configuration from the device rather than from
marketing copy.

## What the board reported before any reflash

`esptool` against the as-shipped board:

```

Features: WiFi, BLE, Embedded PSRAM 8MB (AP_3v3)
```

The shipped partition table is Waveshare-custom — the app is at `0x110000`, not the

```

storage,    data, spiffs,  0xc90000, 3520K
```

Reading the app descriptor at `0x110000` identifies the shipped firmware as
`esp-brookesia`, built `May 27 2026 09:39:19` against IDF `v5.5.4-dirty`.

The whole 16 MB was dumped to `ref/firmware/factory-backup-16MB-20260905.bin`
(sha256 `6f188fb9d35ee793a3423934a4fa4e7c1fef9cc9dae76f9f177dabe854a6cdb3`) **before**
the first reflash, so the as-shipped state — including the populated `assets` and
`storage` SPIFFS partitions — is recoverable.

## The question that mattered: V1 or V2

Waveshare ships two revisions under one product name:

| | V1 | V2 |
|---|---|---|
| Display controller | SH8601 | CO5300 |
| Touch controller | FT3168 (`0x38`) | CST820 (`0x15`) |

This is not cosmetic. Reading the BSP source (`waveshare/esp32_s3_touch_amoled_1_8`
v2.0.3) shows an asymmetry worth knowing about:

- The **panel** driver is hard-coded: the BSP includes only `esp_lcd_co5300.h` and calls
  `esp_lcd_new_panel_co5300()`. There is no SH8601 path.
- The **touch** driver is auto-detected at runtime: it probes the CST816S address, and
  falls back to FT5x06 if that does not answer.

So on a V1 board this BSP would bring touch up correctly and then drive the panel with
the wrong controller — a failure mode that does not announce itself. The revision has to
be established before writing display code.

**Method:** rather than reading a sticker, `projects/bringup-01` scans the shared I²C bus
and infers the revision from which touch controller answers, mirroring the BSP's own
probe order.

**Result:** `0x15` answered and `0x38` did not → **this is a V2 board** (CST820 + CO5300).
Consistent with the shipped firmware date (2026-05-27) sitting alongside the vendor's V2
factory image (`...-V2-FactoryXiaozhi_260601.bin`).

## Full I²C census

```
0x15  CST820 capacitive touch (V2)
0x18  ES8311 audio codec
0x20  TCA9554 I/O expander
0x34  AXP2101 PMU        — CHIP_ID (reg 0x03) = 0x4a
0x51  PCF85063 RTC
0x6b  QMI8658 6-axis IMU — WHO_AM_I (reg 0x00) = 0x05
```

Six devices, all present, on SDA=15 / SCL=14. The two parts that publish an identity
register were read back rather than merely probed, so their presence is confirmed by
content and not just by an ACK.

Note the TCA9554 at `0x20`: the product page does not mention an I/O expander, but the
BSP depends on it for the display and touch power and reset rails. `bsp_io_expander_init()`
has to run before either.

## Finding: the vendor defaults leave a third of the clock on the table

The first build used the vendor example's `sdkconfig.defaults` (target, flash mode/size,
PSRAM mode/speed). It booted with:

```
I (519) cpu_start: cpu freq: 160000000 Hz
```

160 MHz is the ESP-IDF default for the S3; the vendor defaults never set the frequency.
Adding `CONFIG_ESP_DEFAULT_CPU_FREQ_MHZ_240=y`, deleting the stale generated `sdkconfig`,
and reflashing gives `cpu freq: 240000000 Hz`. This is now in `/build` as a required line
for every new project on this board.

## Memory, measured

```
PSRAM : 8388608 bytes total, 8386192 bytes free
Internal heap : 372511 bytes free
```

Boot detail: AP Memory gen-3 octal PSRAM, 64 Mbit, 80 MHz, 3 V, hybrid-wrap 32-byte
burst, 10-cycle fixed read latency. Internal RAM comes back as 326 KiB + 21 KiB +
32 KiB DRAM + 7 KiB RTCRAM.

For context: one full-screen RGB565 framebuffer at 368×448 is 330 KB. Nearly the whole
internal heap. Display buffers belong in PSRAM on this board, not internal RAM.

## Toolchain notes

- The BSP declares `idf: ">=5.5,<6.1"`. v5.5.3 works; IDF 6.1+ will fail dependency resolution.
- `idf.py monitor` is unusable from a non-TTY shell. Serial capture uses pyserial with
  `dtr`/`rts` set to `False` **before** `open()`, then an explicit RTS pulse to reset the
  chip into the app — otherwise opening the port drops the S3 into download mode via its
  native USB-Serial/JTAG. Recipe in `.claude/commands/monitor.md`.
- Changing `sdkconfig.defaults` after a first build does nothing until the generated
  `sdkconfig` is deleted. This cost one confusing rebuild.

## Display bring-up, and a correction

`projects/01_project_template` was then built to take the stack the rest of the way:
`bsp_display_start()`, brightness, an LVGL screen with a tap counter. It came up first try:

```
I (460) co5300_spi: LCD panel create success, version: 2.1.0
I (666) ESP32-S3-Touch-AMOLED-1.8: Touch CST816S 0x15 found
I (668) CST816S: IC id: 183
I (670) app: display up: 368x448, touch indev registered
```

The CST816S driver reporting `IC id: 183` on the CST820 is the expected outcome of the
register compatibility between the two parts, and independently corroborates the V2 call.

**Correction to the first draft of these notes.** The initial CLAUDE.md claimed the TCA9554
gates the display and touch power rails and that `bsp_io_expander_init()` must run first.
That was carried over from the C6 sibling board, where it is true, and it is **wrong here**.
Reading the BSP source settles it: `io_expander` appears in exactly one function,
`bsp_io_expander_init()` itself, and nothing in the BSP ever calls it. The template
confirms it empirically — it never initialises the expander and gets both a working panel
and a registered touch indev.

What the expander actually does on this board is still open. The schematic shows a
TCA9554PWR with its lines labelled `EXIO0`–`EXIO7` and a `DSI_PWR_EN` net in the same
area, but the extracted text is too layout-mangled to trace nets reliably. Recorded as
unknown rather than guessed.

The lesson generalises: the C6 board is the closest relative and therefore the most
dangerous source of assumptions. Same panel size, same PMU/RTC/IMU family, different
display controller, different pins, different expander role.

## Memory, after display bring-up

With LVGL running and a screen drawn: internal heap ~205–243 KB free, PSRAM ~8.24 MB free.
The BSP allocates draw buffers with `buff_spiram = true`, so the panel costs internal RAM
only for the LVGL task and the SPI DMA descriptors.

An LVGL app also overflows the default 1 MB app partition, so the template ships a
`partitions.csv` (4 MB `factory`, 4 MB `storage` SPIFFS under the label
`bsp_spiffs_mount()` expects).

## State at the end of the session

Toolchain verified end to end: build → flash → boot → validate, twice (once to find the
160 MHz default, once to confirm the fix). `projects/bringup-01` is the reusable scaffold
and the check to re-run on any new unit.

Two projects: `bringup-01` (hardware census) and `01_project_template` (display + touch +
LVGL, the scaffold for real work).

Not yet exercised: audio, SD, Wi-Fi, PMU, RTC, and the IMU beyond `WHO_AM_I`. Vendor
examples exist for each under `ref/demo/.../examples/esp-idf/`. One item is verified only
up to the driver layer: a **physical tap** has not been logged yet, so touch is confirmed
as "controller found and indev registered" rather than "coordinates arrive". The template
prints `touch #N at x= y=` on each press, so a single tap during a serial capture closes
that gap.
